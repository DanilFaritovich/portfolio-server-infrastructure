# Repository Instructions

This repository is for Ansible-based provisioning of a personal portfolio VPS on Ubuntu. The implemented pipeline is local setup -> bootstrap managed automation access -> verify access -> provision Docker host -> verify Docker -> firewall/SSH host hardening -> verify hardening -> human access -> verify users -> final SSH policy -> verify SSH security -> separately confirmed server operations -> verify operations -> STOP. Application deployment remains separate.

- `playbooks/bootstrap.yml` calls `roles/bootstrap_user`; `playbooks/docker-host.yml` calls `roles/docker_host`; `playbooks/verify.yml` and `playbooks/verify-docker.yml` verify the separate access/Docker stages; `playbooks/harden.yml` calls `roles/host_hardening`, and `playbooks/verify-hardening.yml` uses read-only `library/portfolio_hardening_info.py`; `inventories/production.example.yml` is the only committed inventory. Actual inventories remain local and ignored.
- `plugins/connection/portfolio_password.py` reuses pinned builtin Paramiko with direct plugin options for password-only bootstrap; verification still uses OpenSSH. Core 2.18.6 lacks variable bindings for key lookup/auto-add, so do not restore their deprecated environment/INI settings or suppress deprecation warnings.
- `make deps` uses `scripts/setup.sh` to prepare checksum-verified pinned local uv, managed Python 3.12 in `.tools/python`, `.venv`, and pinned tooling/collections from registries; no system Python or uv is required. `make check` and `make ci` run YAML lint, offline Ansible lint, syntax validation with example inventory, actionlint, and offline access/setup/Docker/hardening tests with synthetic fixtures and mocked commands. Neither contacts production. No safe automatic fixer is configured.
- `make setup` prepares local dependencies and creates missing inventory without overwriting it. `make bootstrap-user` is LIVE/MUTATING with native password prompting and dedicated local key generation; `make verify-access` is LIVE verification as the inventory managed user with key-only login and `sudo -n`. `make docker-host` is LIVE/MUTATING; `make verify-docker` is LIVE verification with a disposable smoke container and possible image-cache changes. Both first verify managed key-only access with strict trust and `sudo -n`. Never run live targets during offline validation. See `README.md` for prerequisites and the access handoff; a bootstrap recap alone is insufficient.
- `make inspect-hardening` is LIVE/read-only: streams the shared hardening inspector over SSH stdin without remote payload files, collects sanitized PASS/WARN/FAIL findings, and exits non-zero only for blockers. Never run it during offline validation. `make harden` is LIVE/MUTATING; `make verify-hardening` is LIVE verification without managed state changes. Both strictly verify every server route in `ssh_listen_ports`; independent key-only access/sudo uses `ssh_verify_ports` (non-empty subset, default all listen ports). `ssh_listen_ports` must include the current inventory port during transition; no fixed role SSH port. Preserve human root/password/keyboard-interactive policy until Stage 4. Support stock active/enabled ssh.socket and ssh.service listener mode without activation-mode migration; reject custom/ambiguous socket overrides, unsupported unmanaged SSH listeners/includes (only an exact preflight-approved set of global legacy Ports in the main file or standard includes can be adopted by `library/portfolio_ssh_adopt.py` after full staged validation) and ambiguous UFW state; never reset/delete rules. SSH rules precede UFW enable; candidate and handler validation precede reload; socket mode validates generated/effective listeners after daemon-reload before an ordered socket/service restart. See the README for recovery/provider prerequisites and migration limits.
- `make reboot-host` is LIVE/MUTATING maintenance: verify managed key-only SSH and `sudo -n`, require interactive confirmation (default deny), use `playbooks/reboot-host.yml` with bounded `ansible.builtin.reboot`, then verify access, Docker and hardening in order using the same inventory/key. Errors stop later checks; retain provider-console recovery access and never retry reboot blindly. Offline checks only syntax-check this playbook and mock reboot/remote execution.
- Stage 4 uses `roles/human_access`, shared `roles/bootstrap_user/tasks/{controller_key,account}.yml`, and `roles/ssh_security`; Make targets are `add-user`, `verify-user`, `secure-ssh`, `verify-ssh-security`. All are LIVE; creation/final policy mutate. Human keys default to `~/.ssh/portfolio-infra/`, optionally ignored `secrets/portfolio-infra/`; never read/upload private material. Public-only imports cannot prove admin access. Re-prove managed and human admin key-only SSH/sudo before final policy, require interactive recovery confirmation, reject all Match blocks/unsupported includes, stage full SSH candidate, preserve Stage 3 ports/socket mode, and stop on pending activation or unmanaged account/privilege state. No automatic fallback downgrade or account adoption. Adding users after final hardening uses managed inventory user/key access.
- Docker safety preflight precedes mutation: fail on conflicting runtime packages, unmanaged daemon/repository configuration, custom service units/drop-ins, key mismatch or orphan runtime data. Never silently remove packages/configuration/data. Official Docker APT packages use `state: present`; only changed validated daemon config triggers a restart. Keep bounded `local` logs, no managed-user Docker-group membership, no application networks.
- `collections.yml` pins collections installed explicitly by setup/deps; keep it outside ansible-lint's automatic requirements discovery. Make prepends the absolute project `.venv/bin` to PATH for matching Ansible subprocesses.

- Use `develop` as the base for task branches and open Pull Requests into `develop`. Do not merge without an explicit request.
- Keep Ansible changes idempotent and reviewable. Use built-in modules where practical, parameterize host-specific values, and limit privilege escalation to tasks that need it.
- Do not contact a live host, including Ansible `--check`, without explicit approval for that operation. CI must use offline checks and must not contact production.
- Do not read, commit, or expose real inventories, private keys, passwords, tokens, or other secrets. Preserve the existing `LICENSE`.
- Load only the applicable core skill from `.agents/skills/` and its topic references when needed. Follow `.codex-standards.lock.yaml` and the `standards-sync` skill for future updates.

- Stage 5 uses `roles/server_operations` and read-only `library/portfolio_operations_info.py`. `inspect-operations` and `verify-operations` stream inspectors through strict SSH stdin without remote payload/cache writes; `setup-operations` requires managed preflight and default-deny TTY confirmation. Preserve Stage 1–4; never auto-reboot, prune, vacuum, remove packages or reset unrelated configuration. Only Ubuntu security origin updates, bounded journald and stock maintenance timers are managed; incompatible existing container logging and unsafe or unresolved policy/unit/path conflicts block setup. Native read-only apt-config verifies current and prospective effective policy in source order without filename exceptions; standard periodic and independent journald settings may coexist. Offline tests mock every probe; live verification and changed=0 remain operator checks.

- Stage 6 task 1: explicit inventory access uses `bootstrap_login_user` only for initial password bootstrap and `ansible_user`/`ansible_private_key_file` for every managed Stage 1–5 path. The three fields must be set together. Legacy inventories without the two new fields retain the old initial-login/ansible-key behavior. Conflicting key overrides fail before host contact. Migrate secured hosts through existing `add-user` admin access and independent candidate-inventory verification; never automatically switch inventory, delete accounts or reopen SSH policy.

- Stage 6 task 2: `generate-user-key` and `show-public-key` are local-only; generation reuses locked non-overwriting key preparation with native passphrase prompting. `show-controller` only validates local key/trust and prints inventory access. `connect-controller`/`connect-user` open LIVE interactive key-only SSH with strict existing known_hosts trust and the selected agent identity; no auto-trust, client-config overrides or forwarding. No account creation or provisioning is bundled. Stage 1–5 automation remains agent-independent. Offline tests use synthetic keys, mocked SSH and local `ssh -G` configuration parsing only.

- Stage 6 task 3: `list-users`, `show-user`, `list-user-keys` stream read-only VPS state; `add-user-key`, `revoke-user-key`, `remove-user` stream `scripts/user_management.py` with the shared human inspector. Exact key ownership uses protected server-side `<user>.keys.json` ledgers, never a local cache; legacy keys require explicit identical-line registration. Never adopt unmanaged accounts, overwrite/revoke unmanaged keys, or target root/current controller. Destructive operations require fresh separate `RECOVERY_USER`/`RECOVERY_KEY` human-admin SSH/sudo proof, unchanged server snapshots and default-deny TTY confirmation. Removal blocks unmanaged keys/processes/hooks, revokes keys/sudo and uses non-forced userdel without file removal; protected receipts block recreation. No SSH policy changes or blind retries. Existing-user `add-user` uses the additive engine and refuses privilege/group migration; public imports remain independently unverified. All checks remain offline; Stage 6 task 4 is separate.

- Stage 6 final review: OpenSSH wrapper transports ignore client config and forwarding; selected human/recovery identities may use their agent, automation remains agent-independent. Recovery public identity must differ from the controller's, including across copied paths. Shared key paths reject OpenSSH expansion tokens; public key confirmation escapes terminal controls. See both READMEs for the manual LIVE integration checklist and partial-failure recovery; offline success is not live access/idempotency evidence.
