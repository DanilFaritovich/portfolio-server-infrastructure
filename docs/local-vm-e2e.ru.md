# E2E на локальной Ubuntu VM

[English](local-vm-e2e.md) | **Русский**

Это **интерактивная локальная интеграционная проверка**, которая не входит в
`make check` и CI. Она использует KVM, `qemu:///system`, virt-install, официальный
облачный образ Ubuntu amd64 из реестра и cloud-init. Того же гостя можно
просматривать через virt-manager. GNOME Boxes не используется.
Развёртывание приложений не входит в сценарий. Успешные офлайн-проверки не
доказывают работоспособность реального доступа, совместимость пакетов, поддержку
снимков или идемпотентность.

## Подготовка хоста (явное согласие оператора)

Пригодность хоста определяется его возможностями: **Linux x86_64**, аппаратная
виртуализация, работающие QEMU/KVM и системный libvirt, необходимые инструменты,
права доступа и безопасное хранилище. Разрешающего списка релизов Ubuntu для хоста
нет. Нужны как минимум 2 доступных ядра CPU, 4 GiB памяти для гостя и достаточно
места для диска qcow2 размером 25 GiB, облачного образа и внутренних снимков.
Поддержка гостевых ОС ограничена профилями реестра ниже; пригодность хоста не
расширяет список поддерживаемых гостевых ОС.
Сначала выполните `make deps`, чтобы подготовить локальные Python-инструменты
проекта; никогда не запускайте `make` от root.

Системные инструменты гипервизора запускаются без virtualenv и Python-окружения
контроллера в окружении дочернего процесса. В частности, `/usr/bin/env python3`
в virt-install должен находить системный Python с модулями gi/libvirt из
дистрибутива; команды контроллера и Ansible в сценарии сохраняют закреплённые
версии инструментов.

`make e2e-prepare` проверяет флаги виртуализации CPU, установленные пакеты и
команды, доступ к `/dev/kvm`, действующие группы libvirt/kvm, доступ к
`qemu:///system` без sudo, возможности KVM x86_64, владельца и режим каталога
дисков. Изменения хоста допускаются только для нового стенда. Известные изменения
пакетов, групп и хранилища объединяются в один предварительный план и одно
подтверждение через TTY с отказом по умолчанию; перед выполнением повторно
проверяется неизменность зафиксированного состояния. Создание VM включается в
план, только если текущие группы уже действуют; иначе этот запуск завершается
с требованием перезагрузки. Штатная аутентификация sudo остаётся отдельной.
Новые сведения о группах или хранилище, обнаруженные после установки, чтение
настроек QEMU с повышенными правами, перезагрузка и подтверждение консольного
восстановления/выключения для baseline требуют отдельных конкретных согласий.
Разрешение действует только в рамках текущего запуска:

1. Недостающие зависимости перечисляются до предложения выполнить
   `sudo apt-get update` и
   `sudo apt-get install --no-install-recommends --no-upgrade --no-remove`
   **только для недостающих пакетов**. Проверенное соответствие пакетов
   выбирается лишь тогда, когда os-release указывает Ubuntu или Debian и
   доступны apt-get и dpkg-query, без ограничения номеров релизов. Наличие apt
   или одного ID_LIKE не доказывает совместимость. Набор пакетов:
   qemu-system-x86, qemu-utils, libvirt-daemon-system, libvirt-clients, virtinst,
   cloud-image-utils, openssl, iproute2 и openssh-client. Установленные пакеты
   не переустанавливаются; если пакет установлен, но его исполняемый файл не
   найден, PATH или пакет нужно исправить вручную. Штатные запросы sudo и apt
   остаются интерактивными. Ошибка останавливает выполнение без повтора.
   Другие менеджеры пакетов, неизвестные сведения об ОС или отсутствие apt/dpkg
   никогда не запускают автоматическую установку: недостающие команды выводятся
   с указанием установить их вручную. Вручную подготовленный хост может
   продолжить без поддержки менеджера пакетов, если все инструменты доступны
   и дальнейшие проверки возможностей, доступа и хранилища успешны.
   Имена пакетов для неподдерживаемых менеджеров не подбираются автоматически.
2. Известное недостающее членство в libvirt/kvm включается в план; применяется
   только добавление через `usermod -aG`. **Доступ к libvirt эквивалентен правам
   root**; предоставляйте его только доверенным локальным администраторам.
   Если настроенные группы ещё не действуют в текущем сеансе, prepare успешно
   завершается с требованием перезагрузки до создания дисков/VM.
   Интерактивное меню предлагает **Reboot now** (перезагрузить сейчас) или
   **Reboot later** (перезагрузить позже):

   ```text
   ✓ Host permissions configured successfully.
   A system restart is required to activate new permissions.

   [1] Reboot now (recommended)
   [2] Reboot later

   Choose [1/2]:
   ```

   Reboot now выводит `After rebooting, run: make e2e-prepare`, предупреждает о
   несохранённых данных и требует отдельного подтверждения `[y/N]` с отказом
   по умолчанию. После освобождения блокировки стенда CLI выбирает **один**
   механизм по возможностям локального сеанса, без проверки версий ОС:

   - Локальный GNOME X11/Wayland: `gnome-session-quit --reboot` с обычным
     подтверждением рабочего стола и обработкой запретов на перезагрузку
     (inhibitors). GNOME должен быть точным элементом списка
     `XDG_CURRENT_DESKTOP`, разделённого двоеточиями; только если переменная
     не задана, GNOME может определяться по специфичному для него значению
     `XDG_SESSION_DESKTOP`. Нужны соответствующая переменная дисплея
     (`DISPLAY` или `WAYLAND_DISPLAY`) и адрес Unix D-Bus сеанса.
     Для неполного сеанса GNOME или отсутствующего инструмента выводятся
     инструкции для ручных действий; перехода к systemctl нет.
   - Другие локальные сеансы Linux/systemd: `systemctl --check-inhibitors=yes
     --no-ask-password reboot`. Должны существовать каталог времени выполнения
     systemd и systemctl, а тип сеанса должен быть поддерживаемым графическим
     или консольным либо не заданным для обычного локального терминала.
     Системная авторизация и запреты на перезагрузку учитываются даже при
     перехвате вывода дочернего процесса.

   Запуск от root, не-Linux, SSH и удалённые/неоднозначные сеансы
   `XDG_SESSION_REMOTE` отклоняются. Sudo, принудительная перезагрузка, обход
   inhibitors и автоматическая попытка второго механизма после ошибки
   отсутствуют. GNOME может показать дополнительное подтверждение рабочего
   стола; успешный код завершения инструмента означает только отправку запроса,
   а не завершённую перезагрузку.

   При ошибках выводится краткая статическая причина: отсутствует инструмент
   или возможность сеанса, inhibitor, отказ авторизации, неподдерживаемый
   параметр, недоступная служба сеанса/системы, ошибка выполнения, тайм-аут
   или прерывание. Диагностика дочернего процесса классифицируется по тексту
   на английском без вывода исходного stderr, идентификационных данных,
   путей или управляющих символов терминала. Для нераспознанной диагностики
   сообщаются код завершения и безопасная общая причина.
   GNOME может вернуть ноль после неудачного вызова D-Bus; наличие stderr
   всё равно делает результат неподтверждённым. Тайм-аут, прерывание или иной
   неподтверждённый результат не доказывают отмену: проверьте состояние системы
   перед любым ручным повтором. Используйте штатное действие Restart рабочего
   стола или попросите администратора безопасно перезагрузить систему.
   Reboot later, пустой выбор, отказ от подтверждения или прерванный ввод
   сохраняют настроенные группы и успешно завершают команду с инструкцией
   повторного запуска. Без TTY выводятся только инструкции для ручных действий.
   Автоматической перезагрузки без участия оператора нет.

   После перезагрузки снова выполните `make e2e-prepare` (повторите `E2E_DISTRO`,
   если выбирали его). Команда заново проверит действующие группы, доступ к
   KVM/libvirt и хранилище, затем продолжит с существующими подтверждениями;
   дополнительные команды для настройки прав не нужны. Ошибки настройки групп
   или неподтверждённое членство по-прежнему блокируют выполнение.
   При уже действующих группах это меню не появляется. До вступления прав
   в силу гостевая VM и состояние стенда не создаются.

3. Отсутствующий каталог `/var/lib/libvirt/images/portfolio-e2e-<UID>`
   предлагается в плане, если известны идентичность QEMU и защищённые родительские
   каталоги. Исключительный `mkdir` отклоняет путь, появившийся параллельно;
   только новый каталог получает владельца-контроллера, штатную группу
   `libvirt-qemu` и режим 2750. Финальный chmod также использует sudo:
   владелец вне группы QEMU не может сохранить setgid при непривилегированном
   chmod. Родительские пути уже должны быть защищёнными каталогами root.
   Существующие владелец и группа никогда не исправляются автоматически.
   Для пустого выделенного каталога, оставшегося после прежней ошибки chmod,
   prepare может включить завершение перехода из режима 0750 в 2750 в
   согласованный план той же команды. Для этого нужны правильные владелец
   контроллера и группа QEMU, отсутствие символьных ссылок и ACL доступа,
   неизменное зафиксированное состояние каталога и пустое содержимое после
   подтверждения. Исключение не распространяется на существующий стенд,
   данные VM, другие режимы или расхождения владельца/группы.

Каталог с setgid передаёт создаваемым файлам группу QEMU. Новые диски qcow2
имеют режим 0660 для чтения/записи QEMU; seed ISO — 0640 для чтения.
Оба источника дисков содержат `seclabel model="dac" relabel="no"`, поэтому
libvirt не меняет их владельца-контроллера. AppArmor остаётся включённым.
Групповая запись допускается только для принадлежащего контроллеру qcow2 с
режимом 0660 и группой защищённого каталога хранилища; для seed-файлов и других
путей сохраняются более строгие проверки.
Существующие стенды не переписываются и не исправляются. Нестандартные
идентичности QEMU, небезопасные пути, отсутствующие родительские каталоги,
ошибки прав KVM/устройств, авторизации/службы libvirt или конфликты политик
безопасности хоста требуют ручной диагностики администратора. Существующие
соглашения о группах libvirt/kvm и штатном хранилище libvirt-qemu сохраняются;
пригодность Linux-хоста не означает автоматическую миграцию конфигурации
гипервизора. Подготовка не меняет конфигурацию libvirt, не запускает службы,
не ослабляет AppArmor/ACL и не предоставляет sudo.
Отказ от подтверждения оставляет последующие шаги невыполненными; уже
согласованные изменения пакетов или групп сохраняются. Автоматического
отката или очистки нет.

Подготовка проверяет `/etc/libvirt/qemu.conf`, чтобы отклонить нестандартные
идентичности QEMU до создания дисков. Если контроллер не может прочитать этот
файл root, `make e2e-prepare` предлагает отдельное подтверждение чтения через
sudo с отказом по умолчанию. Пройдите штатную аутентификацию sudo в рамках
той же команды. Изолированный системный интерпретатор Python проверяет
безопасность файла, неизменность метаданных идентичности/содержимого и штатные
настройки пользователя/группы QEMU без вывода конфигурации.
Менять ACL, владельца или права не требуется. Отказ, ошибка sudo,
нестандартные идентичности или параллельные изменения файла останавливают
подготовку до создания дисков/VM; после неудачного чтения идентичность по
умолчанию не предполагается.
Ошибки CLI сообщают операцию и безопасные категории ошибок ОС (например,
`E2E STOP (fixture lock)` с `EROFS` указывает на файловую систему только для
чтения или sandbox контроллера). Ошибки дочерних процессов также называют
фиксированную операцию (например, активацию сети или создание XML домена)
и код завершения без аргументов и вывода процесса. Эта диагностика не
доказывает отмену и не разрешает повтор.
Произвольный текст исключений, пути и вывод дочерних процессов исключаются.
Перед новым запуском диагностируйте ограничения контроллера; сами по себе
они не доказывают сбой VM или libvirt.

Необязательный графический просмотр остаётся ручным действием оператора
(`virt-manager`). Готовый существующий стенд заново проверяется и показывается
без изменений хоста, загрузок или пересоздания гостя. Частично подготовленные
стенды останавливают выполнение без возобновления подготовки.

## Подготовка и первый запуск

После отдельного разрешения на реальное выполнение локальной VM:

```sh
make e2e-list-distros  # локальный реестр, без проверок хоста/сети
make e2e-prepare      # по умолчанию Ubuntu Server 24.04 LTS
# Альтернатива для НОВОГО стенда:
# make e2e-prepare E2E_DISTRO=ubuntu-22.04
make e2e-status
make e2e-test E2E_FROM=bootstrap
```

Значения по умолчанию: 2 vCPU, 4096 MiB RAM, qcow2 25 GiB, выделенная NAT
`192.168.231.0/24`, зарезервированный в DHCP адрес гостя `192.168.231.10`,
SSH-порт 22. Только для нового стенда можно задать `E2E_CPUS`, `E2E_MEMORY`,
`E2E_DISK_GB`, `E2E_SUBNET` (неиспользуемую частную `192.168.x.0/24`).
Минимальные ресурсы остаются 2/4096/25. Существующие стенды сохраняют
записанные параметры; prepare не меняет размер, конфигурацию и не пересоздаёт
их. Пересечение с маршрутами хоста или сетями libvirt блокирует создание.
NAT даёт исходящий доступ в Интернет для существующих операций APT/Docker;
это отдельный мост, а не ограничение исходящего доступа или изоляция от сети.
Не помещайте production-учётные данные в гостя.

Декларативный [реестр образов](../scripts/portfolio_cli/e2e_distros.yml)
поддерживает только **Ubuntu Server 24.04 LTS (`ubuntu-24.04`)** и
**Ubuntu Server 22.04 LTS (`ubuntu-22.04`)**, обе amd64. В нём записаны
отображаемая идентичность, архитектура, официальные URL образов/контрольных
сумм и проверенные профили совместимости BIOS/qcow2/cloud-init/SSH.
Другие дистрибутивы Linux, архитектуры, UEFI-образы и версии релизов
отклоняются. Jammy и Noble разрешены текущими ролями настройки; обе используют
одинаковую начальную настройку root-пароля через cloud-init и штатную обработку
службы/сокета SSH. Консервативный аппаратный профиль virt-install `ubuntu22.04`
работает с обеими версиями и доступен в osinfo-db контроллера Jammy; он не
меняет гостевой образ. Тесты с mock-объектами покрывают оба выбора; реальная
совместимость пакетов, SSH и сходимости всё равно требует отдельно разрешённых
интеграционных прогонов на каждой версии.

Новое состояние (схема 2) записывает выбранный дистрибутив, который показывает
`e2e-status`. Существующие стенды схемы 1 сохраняют исходную идентичность Noble
без перезаписи состояния. Если для существующего стенда не задать `E2E_DISTRO`,
сохраняется записанный дистрибутив. Явный выбор другого блокируется; только
отдельно подтверждённое удаление позволяет подготовить другой образ.
Существующая VM никогда не перезаписывается.

Образы и SHA256SUMS поступают только из официальных каталогов релизов по HTTPS:
[Ubuntu Noble](https://cloud-images.ubuntu.com/releases/noble/release/) и
[Ubuntu Jammy](https://cloud-images.ubuntu.com/releases/jammy/release/).
Строгая проверка реестра отклоняет недоверенные URL и несовместимые профили,
включая повторяющиеся поля YAML/ID. Перенаправления отклоняются **до перехода**;
загрузка образов игнорирует прокси из окружения. SHA-256 полностью загруженного
образа сравнивается с официальным списком и сохраняется в `image.sha256`.
При необходимости задайте
`E2E_IMAGE_SHA256=<previously verified 64-character lowercase digest>`,
чтобы потребовать конкретную ранее проверенную контрольную сумму релиза из
64 символов в нижнем регистре. Содержимое URL релизов может меняться; любое
несовпадение останавливает подготовку. Список контрольных сумм аутентифицируется
через HTTPS, а не независимо проверенной подписью GPG.

Prepare запрашивает согласие на создание с отказом по умолчанию (включая
установку guest-agent) и дважды новый одноразовый пароль root со скрытым вводом:
не менее 12 печатных ASCII-символов. Короткий/не-ASCII ввод или несовпадение
получают конкретное безопасное сообщение и повторный локальный ввод внутри
prepare до создания стенда/VM. Ctrl+C отменяет ввод; EOF или прерывание
останавливают подготовку. Пароль никогда не попадает в argv, окружение,
inventory, отчёты или Git. Только его хеш SHA512-crypt попадает в приватные
артефакты cloud-init и seed. Используйте уникальный одноразовый пароль и
сохраните его в менеджере паролей: обёртка не сможет показать или восстановить
его позже. cloud-init создаёт начальный доступ root через консоль и SSH по
паролю и маркер UUID стенда, обновляет индекс APT гостя и устанавливает/запускает
`qemu-guest-agent` для локальных проверок готовности. Поэтому при первой
загрузке гостю нужны работающие NAT/DNS и доступ к репозиториям Ubuntu.
Обновление пакетов не запрашивается. Вся управляемая настройка остаётся в
существующих ролях Ansible.

Prepare запускает VM и выводит её UUID и команду консоли. В другом терминале
откройте `virsh -c qemu:///system console <UUID>` (или последовательную консоль
virt-manager), войдите как root и:

1. Выполните `cloud-init status --wait`; потребуйте успешного завершения без ошибок.
2. Выполните `sshd -t`, `sshd -T | grep -E '^(permitrootlogin|passwordauthentication) '`
   и убедитесь, что оба значения — `yes`. Проверьте
   `systemctl is-active ssh.socket` или `systemctl is-active ssh.service`
   в соответствии со штатным режимом слушателя.
3. Выполните `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`; сохраните fingerprint.
   Убедитесь, что вход root через консоль работает независимо от SSH, затем
   выйдите из консоли через Ctrl+]. Ручной `poweroff` не требуется.
4. Вернитесь в prepare и подтвердите эти проверки и согласие выключить гостя
   и создать baseline. Обёртка повторно проверит принадлежащие стенду ресурсы
   и до 300 секунд будет ожидать автоматическую готовность гостя через локальный
   канал QEMU guest-agent: UUID гостя должен совпадать, cloud-init должен
   завершиться без ошибок, конфигурация SSH должна пройти проверку,
   `ssh.service` и `systemd-logind` должны быть активны, а устройство ввода
   Power Button — присутствовать. Проба выполняет короткие команды только
   для чтения и собирает лишь коды завершения, никогда не вывод команд.
   Подключение SSH, пароль и принятие доверия к хосту не участвуют. Это
   предотвращает выключение после слишком раннего подтверждения, когда
   обработчик кнопки питания гостя ещё не загрузился. Затем запрашивается
   корректное выключение через `virsh shutdown` с ожиданием `shut off`
   до 120 секунд. Уже выключенный гость не требует запроса выключения;
   за уже выключающимся гостем только наблюдают. Принудительного выключения нет.
   Отказ от подтверждения оставляет гостя работающим. Ошибка/тайм-аут готовности
   предотвращают выключение и создание baseline. Повторно опрашивать можно
   только точное состояние agent-not-connected во время загрузки по проверенным
   английским и русским ответам. Демон libvirt может вернуть переведённый
   текст ошибки, даже если клиент использует `LC_ALL=C`. Ошибки транспорта/
   протокола, потеря проб и ошибки гостя немедленно останавливают выполнение.
   Тайм-аут выключения, неожиданное состояние или ошибка запроса также
   останавливают подготовку с сохранением частичного стенда.
   Обёртка создаёт/проверяет внутренний снимок **baseline**, отмечает стенд
   готовым и снова запускает его. Перед тестированием дождитесь DHCP.

Неподдерживаемый механизм снимков останавливает подготовку с сохранением
частичного стенда. Перехода к другому механизму или автоматического исправления
нет. Распознанные ошибки транспорта guest-agent сообщают фиксированный
безопасный диагноз без раскрытия аргументов команд, вывода гостя или исходной
диагностики libvirt. При STOP транспорта готовности ручная проверка только
для чтения выглядит так:

```sh
LC_ALL=C virsh -c qemu:///system qemu-agent-command <UUID> --timeout 5 '{"execute":"guest-ping"}'
```

Она проверяет только связь с агентом. В консоли гостя проверьте
`systemctl is-active qemu-guest-agent` и условия готовности выше.
Проба готовности при подготовке проверяет первую загрузку cloud-init,
которая явно запускает `ssh.service`. После последующей перезагрузки штатная
активация через сокет может оставить эту службу неактивной, а `/run/sshd`
отсутствующим до активации SSH; поэтому проба готовности первой загрузки
может оставаться в ожидании даже при активном `ssh.socket`. Она не запускает
SSH и не создаёт каталоги времени выполнения.
Успешный последующий ping или проба готовности не объясняют исходную ошибку
и не завершают подготовку; частичный стенд сохраняется и не может быть
автоматически продолжен. Проведите диагностику перед любым отдельно
подтверждённым удалением или новой подготовкой.

Снимок содержит полное определение принадлежащего стенду домена, не содержит
состояния памяти и использует только внутренний снимок диска qcow2; см.
[семантику снимков libvirt](https://libvirt.org/formatsnapshot.html).

## Изоляция и выполнение сценария

Ресурсы именуются `portfolio-e2e-<controller UID>`. Принадлежность требует
записанных UUID, метаданных libvirt в выделенном пространстве имён, фиксированных
путей дисков и выделенной сети. Одни имена никогда не дают полномочий.
Проверяются метаданные и постоянный/текущий XML домена. E2E отклоняет
дополнительные диски, цепочки backing-файлов, проброшенные устройства,
внешние снимки/снимки памяти, подключения к чужим сетям и небезопасные
локальные пути. Неблокирующая блокировка рядом с каталогом стенда сериализует
команды стенда на всё время работы дочерних CLI; её inode сохраняется после
удаления. Другие администраторы libvirt должны вручную сериализовать операции;
они могут обойти эту локальную блокировку.

Inventory, состояние, исходный образ/cloud-init, ключи, HOME, known_hosts и
безопасные логи init хранятся в `~/.local/share/portfolio-e2e/` (вне репозитория,
с приватными правами). Только диски и seed находятся в выделенном каталоге
образов libvirt. Inventory создаётся с явно заданным начальным доступом root
и управляемым доступом `ansible`; это не редактируемая конфигурация.
Точное содержимое inventory, активные принадлежащие стенду VM/NAT,
соответствующая MAC-адресу аренда DHCP и маршрут хоста через принадлежащий
стенду мост повторно проверяются перед запуском CLI. `INVENTORY`,
`AUTOMATION_KEY`, HUMAN_* и произвольные переопределения Ansible из вызывающей
оболочки исключаются из дочерних процессов E2E; `E2E_INVENTORY` запрещён.
Переопределения аргументов CLI и чужие inventory отклоняются до настройки.
Дочерний процесс закрепляет known_hosts стенда в OpenSSH и использует
изолированный HOME для Paramiko. Production-inventory и приватные материалы
никогда не читаются E2E.

`e2e-test` использует **настоящий `make init-server`**, существующий начальный
вход по паролю, роли Ansible, независимые проверки SSH только по ключу/sudo
и существующие проверки этапов. Один предварительный план сценария с отказом
по умолчанию покрывает перечисленные операции, включая подтверждение
возможности восстановления через консоль провайдера. Сначала он создаёт
отдельный пользовательский ключ `e2e_admin` через существующий локальный
процесс работы с ключами. Агент не запускается. Для зашифрованных ключей
используйте существующий агент вызывающей оболочки и примите действие
загрузки в агент из плана; для существующей незагруженной идентичности
выполните в той же оболочке:

```sh
make load-user-key \
  HUMAN_KEY="$HOME/.local/share/portfolio-e2e/home/.ssh/human/admin_ed25519"
```

Доверие SSH никогда не принимается автоматически. При первом bootstrap
сравните показанный fingerprint с fingerprint из консоли VM, прежде чем
принимать доверие. Сохраняйте консольный доступ для восстановления на каждом
этапе и при перезагрузке. Пароль root остаётся действующим в последовательной
консоли после окончательного запрета root/парольного входа по SSH.

Сценарий выполняет:

- Выбранный оператором начальный этап `INIT_FROM` через `E2E_FROM` или штатный
  запрос: для новой установки используется `bootstrap`; продолжение требует
  явно выбранного этапа после диагностики. Допустимы `bootstrap`, `docker`,
  `hardening`, `human`, `ssh`, `operations` и `verify`; значения по умолчанию нет.
  Штатная проверка предыдущих этапов остаётся обязательной.
- Проверку всех этапов через `init-server`; отдельные пробы SSH проверяют UUID
  стенда, управляемую идентичность, sudo, активность/включение/работу Docker,
  активность UFW, штатный слушатель SSH, окончательный запрет root/пароля,
  таймеры обслуживания и journald. Существующая проверка безопасности SSH
  также проверяет предлагаемые методы аутентификации и независимо доказывает
  доступ пользовательского администратора.
- Повторную проверку сходимости с `docker`, включённую в тот же план сценария.
  Потоковые итоговые сводки Ansible или точные свидетельства отсутствия
  необходимых управляемых изменений должны подтвердить `changed=0` для
  настройки; существующая проверка Docker с одноразовым smoke-контейнером
  должна сообщить ровно три намеренных изменения создания/запуска/удаления
  контейнера. Парсер не сохраняет лог вывода. Отсутствующие свидетельства или
  свидетельства изменений означают неуспех сценария; аддитивное поведение
  работы с пользователями остаётся покрытым существующими проверками и
  офлайн-тестами движка.
- Существующий `reboot-host`, явно включённый в план сценария, полную
  окончательную проверку и повторные независимые пробы. Независимо полученные
  boot ID должны различаться.

Ошибки немедленно останавливают выполнение, сохраняют состояние гостя/локальные
данные и никогда не запускают сброс/повтор. После частичного теста не выдаётся
автоматический отчёт об успехе. Очищенные от чувствительных данных штатные
JSONL-логи init остаются в `tmp/` стенда; они не разрешают продолжение.
При ошибках вывода/проб проверьте консоль и существующие штатные инспекторы
только для чтения. Не очищайте маркеры незавершённой активации/защитные записи
и не считайте отмену доказанной.

Отдельные проверки жизненного цикла пользователей/ключей на работающем
настроенном стенде описаны в разделе [Проверьте пользователей и ключи](operator-guide.ru.md#проверьте-пользователей-и-ключи).
Эти обёртки сохраняют собственные подтверждения и независимые доказательства
доступа для восстановления; план сценария их не разрешает.

## Диагностика сокета SSH (только чтение)

Генератор Ubuntu Noble намеренно удаляет
`/run/systemd/generator/ssh.socket.d/addresses.conf`, когда действующая
конфигурация SSH соответствует стандартному порту 22 пакета. Исходный Noble
использует один двухстековый `ListenStream=22`; обновления Noble используют
`0.0.0.0:22`, `[::]:22` и `BindIPv6Only=ipv6-only`. Поэтому само по себе
отсутствие drop-in не означает ошибку активации. См. исходный код Ubuntu:
[исходный генератор](https://git.launchpad.net/ubuntu/+source/openssh/tree/debian/patches/sshd-socket-generator.patch?h=ubuntu/noble),
[обновлённый генератор](https://git.launchpad.net/ubuntu/+source/openssh/tree/debian/patches/sshd-socket-generator.patch?h=ubuntu/noble-updates)
и [обновлённый unit пакета](https://git.launchpad.net/ubuntu/+source/openssh/tree/debian/systemd/ssh.socket?h=ubuntu/noble-updates).

После отдельного разрешения на инспекцию конкретного стенда только для чтения
используйте существующий инспектор Stage 3 с его изолированным inventory,
выбранным ключом контроллера и доверием стенда. Отчёт показывает
`SSH socket route source` и нормализованные маршруты `on-disk`, `loaded`,
`live` и `desired`. Для этого E2E-inventory каждый должен охватывать `ipv4:22`
и `ipv6:22`; после их согласования перезагрузка сокета не нужна.
Инспекция всё равно возвращает NOT READY при наличии записи незавершённой
активации, одновременно собирая независимую диагностику маршрутов.
Она никогда не очищает эту запись.

Чтобы определить пакет VM и вариант загруженных привязок без ещё одного
запуска настройки, оператор может собрать следующие результаты только
для чтения в существующей последовательной консоли гостя:

```sh
dpkg-query -W -f='${Version}\n' openssh-server
systemctl show ssh.socket --property=FragmentPath,DropInPaths,Listen,BindIPv6Only,ActiveState,UnitFileState
cat /proc/sys/net/ipv6/bindv6only
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T | awk '$1 == "port" || $1 == "addressfamily" || $1 == "listenaddress"'
sudo ss -H -ltnp 'sport = :22'
```

Сохраните очищенный от чувствительных данных отчёт инспектора, версию пакета,
код завершения `sshd -t` и эти свойства слушателей/привязок. Не передавайте
полную конфигурацию SSH, учётные данные или приватные ключи. Эти результаты
позволяют отличить допустимое отсутствие стандартного drop-in от ошибки
генерации, расхождения загруженного состояния или отсутствия семейств адресов.
Офлайн-фикстуры воспроизводят первый случай, но не определяют фактический
пакет/состояние VM и не доказывают реальный доступ. После диагностики любая
активация/повтор, согласование защитных записей или повторный прогон
идемпотентности требуют отдельного разрешения; не перезапускайте слушатели,
не очищайте маркеры и не сбрасывайте стенд как диагностический шаг.

## Эксперименты со сбоями и восстановлением (под контролем оператора)

Разрушительные эксперименты намеренно выполняются вручную: нет автоматических
ответов, внесения сбоев или режима автоматического отката. Каждый запускайте
со своего внутреннего диагностического снимка остановленной VM, оставляя
baseline нетронутым. Используйте UUID из status и сначала проверьте XML/консоль.
Примеры команд (действия оператора):

```sh
virsh -c qemu:///system shutdown <UUID>
virsh -c qemu:///system domstate <UUID>  # должно быть shut off
virsh -c qemu:///system domblklist <UUID> --details
# Подставьте проверенную цель seed CD-ROM (обычно sda):
virsh -c qemu:///system snapshot-create-as <UUID> diagnostic-before-failure \
  --memspec snapshot=no --diskspec vda,snapshot=internal --diskspec sda,snapshot=no
virsh -c qemu:///system start <UUID>
```

Никогда не используйте здесь `--disk-only` (выбирает внешние снимки), `--force`,
`--running`, блочные устройства/общее хранилище или снимки работающей VM.
Проверка жизненного цикла принимает только внутренние снимки остановленной VM
с именами `baseline` и `diagnostic-<lowercase-name>`. Поддерживаемые эксперименты
включают прерывание этапа, недоступность SSH во время этапа и существующий
маркер незавершённой активации. После сбоя используйте последовательную консоль
и инспектор соответствующего этапа, докажите, что удалённая работа остановилась,
запишите диагноз, вручную исправьте только выявленную причину, затем явно
выберите начальный этап, например:

```sh
make e2e-test E2E_FROM=hardening
```

Предыдущие этапы должны заново пройти проверку. Незавершённое/неоднозначное
состояние по-прежнему блокирует выполнение. Для разрушительных экспериментов
с политиками или хранилищем вручную восстановите **их диагностический** снимок
только после выключения через консоль и инспекции:

```sh
virsh -c qemu:///system domstate <UUID>  # shut off
virsh -c qemu:///system snapshot-dumpxml <UUID> diagnostic-before-failure
virsh -c qemu:///system snapshot-revert <UUID> diagnostic-before-failure
virsh -c qemu:///system domstate <UUID>  # должно остаться shut off
virsh -c qemu:///system start <UUID>
```

Если восстановление/проверка механизма снимков не удались, STOP. Никогда не
применяйте принудительное восстановление и не меняйте метаданные снимков,
чтобы скрыть несовместимость. Перед продолжением проведите независимую
диагностику. Не сбрасывайте стенд автоматически после неудачных тестов.

## Сброс, удаление и незавершённая подготовка

```sh
make e2e-reset   # отказ по умолчанию; корректная остановка, возврат baseline, запуск
make e2e-delete  # отказ по умолчанию; удаление только проверенных ресурсов стенда
```

Сброс требует готового стенда и проверенного baseline, корректно останавливает
гостя, повторно проверяет принадлежность и снимки, восстанавливает без force,
проверяет, что гость остаётся выключенным, затем запускает его. Локальные
идентичности и совместимое с baseline доверие к хосту сохраняются.
Пароль консоли — исходный пароль baseline. Тайм-аут, приостановленный гость
или неподдерживаемый механизм снимков блокируют выполнение; принудительного
уничтожения нет.

Удаление может убрать частичную подготовку, записанную в журнал состояния,
после явной инспекции и подтверждения. До изменений оно проверяет все
локальные пути, отклоняет символьные/жёсткие ссылки, неизвестные файлы
хранилища или другую VM, ссылающуюся на хранилище/NAT; повторяет проверки
после подтверждения, корректно останавливает принадлежащего стенду гостя,
удаляет его проверенные снимки и определение домена, затем только выделенные
NAT и файлы. Оно никогда не удаляет общие пулы/сети по умолчанию, не следует
символьным ссылкам, не использует шаблоны подстановки или `rm -rf`.
Выделенный каталог хранилища также удаляется; новая подготовка снова предложит
его создание с отдельным согласием. Inode соседней блокировки сохраняется.
Если принадлежащий root родительский каталог мешает непривилегированному
удалению, delete включает действие sudo-rmdir в предварительный план удаления
с отказом по умолчанию до любых изменений. Через sudo удаляется только
проверенный пустой выделенный каталог. Файлы контроллера и состояние сохраняются
до успешного удаления хранилища; права родительских каталогов не меняются,
дополнительная команда оболочки не нужна.
Если удаление прервалось на середине, проверьте фактические ресурсы;
не повторяйте вслепую.

Удаление допускает стандартные права публичных ключей `ssh-keygen` (`0644`,
а также безопасные режимы только для чтения/чтения группой) только для обычных
`.pub` файлов непосредственно в каталогах стенда `home/.ssh/controller`,
`home/.ssh/human` и `home/.ssh/portfolio-infra`. Эти файлы всё равно должны
принадлежать контроллеру, иметь ровно одну жёсткую ссылку и не содержать
компонентов-символьных ссылок в пути; запись для группы/остальных запрещена.
Приватные ключи, `known_hosts`, каталоги и все остальные файлы стенда сохраняют
существующие проверки приватных прав. Никакие права автоматически не исправляются.
Ошибки небезопасного пути и владельца/режима показывают проблемный путь как
экранированную JSON-строку без вывода содержимого файлов. Проверьте этот путь
перед повтором удаления.

Неудачная подготовка сохраняет фазу `preparing`. Другой prepare отказывается
возобновлять, пересоздавать или перезаписывать её. Используйте status/консоль
для диагностики, затем явно удаляйте только после проверки принадлежности.
Утерянное/некорректное состояние, неизвестные ресурсы или расхождения требуют
диагностики администратора; совпадения имён недостаточно для принятия ресурсов
под управление. Старые стенды могут содержать файлы владельца QEMU, оставшиеся
после изменения DAC-меток libvirt, включая seed ISO только для чтения после
выключения. Они по-прежнему блокируют status/удаление; новая политика XML
применяется только к новым стендам и не исправляет владельца существующих
файлов и не возобновляет частичную подготовку.
Не прикладывайте секретные файлы cloud-init или экспорты VM к публичным
сообщениям об ошибках.
